# Module: Concurrency — the strict lane (executors in one shared checkout)

Historical: the dsh kernel and its guard plugins were removed (dsh runs unguarded for simple jobs; git history has them). Formerly loaded from the dsh kernel: this is how a dsh planner routes items to local workers, and the rules here came from failures in shared checkouts. A Claude Code session is not bound by it (`design.md → Claude Code: guidance, not guards`) — it organises branches, worktrees and parallel agents by its own judgment, and only core rule 9's knowledge-base clauses apply to it. Read this module there only as the record of what went wrong in a shared tree.

**The trigger is not how many executors there are — it is whether they share a working tree.** Two writers in one tree race the index, `HEAD` and the files themselves; two writers with no shared filesystem cannot collide at all, however many of them there are. Decide on locality first, then on count:

```
                    where does the executor run?
                                │
        ┌───────────────────────┴────────────────────────┐
   LOCAL — this checkout                     REMOTE / CLOUD — own sandbox
   shares the working tree                   shares only the git remote
        │                                                │
   SEQUENTIAL, always                        PARALLEL fan-out is fine
   branch → work → review →                  N items, N executors,
   gate → merge → next                       one feat/<slug> branch each
```

- **Shared tree → sequential, always.** One executor at a time in the primary checkout: cut its branch, run it, review the diff, gate, merge `--no-ff`, then the next. This is not a degraded mode — it is the only correct one when a tree is shared, and a local subagent (a dsh child, a Claude Code `Agent` with no isolation) always is one.
- **No shared filesystem → parallel is allowed.** A remote executor (Claude Code `Agent` with `isolation: "remote"`, a cloud session) gets its own machine and its own clone and cannot reach the primary checkout, so the invariant this module protects holds by construction. Fan out one item per executor.
- **Local worktrees are a third option, and the last to reach for.** Harness-managed only (Claude Code `Agent` with `isolation: "worktree"`): it creates the worktree, runs the executor in it, and cleans up. Never hand-rolled — no setup scripts, no post-checkout hooks. A project may ban them outright **without** thereby banning remote parallelism: the incidents below were shared-`docs/` failures inside one machine, which a remote executor cannot reproduce.
- **Data for an isolated executor: a pointer, never a symlink.** A worktree or a remote clone holds tracked files only — no `data/`, no venv — and that is the design: tests run against throwaway roots and the gate runs after merge in the primary checkout. When an executor must READ real data, the project's data-root environment variable points at the primary checkout (e.g. `<PROJECT>_DATA=<primary>/data`) — nothing on disk, nothing to stage, nothing to dangle. Executors never write `data/` (rule 9), so two of them reading one root cannot collide. Symlinking data into worktrees is the v1 mechanism behind the four incidents in the history below.
- **Return path — a remote executor pushes its own branch and nothing else.** Standing carve-out to the kernel's never-push rule: an executor may `git push origin feat/<slug>` for the branch it was given — never `main`, never `--force`, never another executor's branch. The orchestrator fetches, reviews the diff, gates and merges locally. Every other push still needs the owner's explicit word.
- **Gates run where the toolchain is** — on the orchestrator's machine, against the MERGED result. A remote sandbox usually has neither the project's toolchain nor its fixtures, and a green gate inside one executor's sandbox says nothing about the merge of N branches.
- **One knowledge-base writer, always.** Records, `findings.md`, INDEX, and `data/` writes stay with the single coordinating session in the primary checkout. Two sessions writing records race the shared `exp_NN` allocation — never do it. Under remote fan-out this comes free: the executor has no `docs/` to write.
- **Commit before you spawn.** Whatever the coordinating session has written to `docs/` — a board status, a `--note`, a scaffolded record — is committed BEFORE a child is started, not at merge time. Between spawn and merge those edits exist only in the working tree the child shares, and a child's `git stash` or `git checkout` takes them with it (it happened twice in one session, after briefs had forbidden it). Enforced by `spawn-guard`: a spawn into a dirty `docs/` is refused with the paths to commit.
- **The brief carries the baseline; the executor never visits `main`.** Every number the executor will be judged against — test count, lint/clippy count, the gate's output — is measured by the orchestrator on `main` before the branch is cut, and written into the brief with the artifact path. An executor with no baseline in hand goes looking for one, and the way it looks is `git stash`, `git checkout main -- .`, a worktree. The brief also states the banned commands once — stash, reset, clean, restore, worktree, `checkout -- <path>`, merge, rebase, push, branch delete — and what to do instead: undo an edit by editing the file back, report a missing baseline rather than measuring it. Enforced by `executor-guard` in every delegated dsh session, because the words alone did not hold.
- **A brief names its files and its done-command, or it is refused (under dsh).** Every spawn carries `Files: <explicit list>` and `Done: <the command that proves it done>` — the removed dsh `spawn-guard` denied one that carries neither marker, isolated child included; the Claude Code half judges the tree only. The file list is the PARENT's to decide, because the parent holds the epic, the item and the board; a child that is not told which files it owns re-derives the scope by searching, which is the slowest and least reproducible way to get it, and two children then edit the same file without either brief saying so. If the list cannot be written, the item is not ready to delegate (`maestro epic item --add` refuses an unscoped item for the same reason, and refuses a wide one that does not declare itself a mechanical pass in `N files in K units`). In one project, 62 children were spawned off ONE item whose scope was never stated: 255 files, discovered afterwards.
- **The dsh planner does not write code (the `root-code-guard` plugin that enforced it was removed).** In a top-level dsh session a write to a TRACKED path outside `docs/` is denied — write/edit tools and file-writing shell commands alike; `docs/`, the instruction files, `.claude/` and untracked paths pass. In one long session the planner wrote its own code at a 200k-token context: both lanes in one agent means the merge is reviewed by the author of the code, and the context that should be steering the epic goes on the diff. A project that really wants the planner to code a small item says so in its own `maestro.toml` (`[agents.dsh] root_writes_code = true`) — a human's call, not the session's. A session on the `item-solo` preset (or `item-solo-ctx<K>k`; env `DSH_TUI_PRESET`) is the executor itself and passes (not ported to dsh 0.2).
- **The harnesses are not mirrors.** Claude Code sessions edit code and are guarded by none of the lane rules here — not root-code, not the brief, not live-child, executor or spawn; they keep only the record-surface guards (records, stamps, kb index) and the gh rule. dsh planners used to get all of it; the plugins are gone. Claude Code is the high-judgment top-level session where the work is thought through and written; dsh is where well-scoped epics and items are routed to local workers, and a shared checkout driven by a router is what these controls police.
- **The brief says how to edit: the `edit` tool for replacements, a script only to move a block, and a re-read after it.** An executor that rewrites files from a `python3 - <<'PY'` heredoc bypasses the edit tool's two guards — read-before-write and the stale-file check — and the guards then turn against it: every later `edit` on that file is refused with "file changed since it was read" until a full re-read, so the script route becomes the cheap one and stays. In one run (a large-file extraction on a local 27B model): 62 heredoc rewrites against 35 edits, 8 refused edits. The one thing the edit tool cannot do is move a block of thousands of lines; that is the only sanctioned script write, and it is followed by re-reading the file before the next `edit`. Scratch copies go under the run's own directory, never `/tmp`.
- **Executor branches are code-only.** Review the branch diff before merge; any path under `docs/`, `data/`, `CLAUDE.md`, or `.claude/` appearing in an executor's diff is a broken invariant — stop and inspect. The executor gets its spec in the task prompt; if it must read a doc, quote it or pass an absolute path into the primary checkout (read-only).


History: v1 shared `docs/`/`data/` into every worktree via symlinks (`setup-worktree.sh` + a post-checkout git hook). That machinery caused four documented incidents (data destroyed by a staged symlink, sessions running with no rules due to broken links, silent backup failure, standing false test failures) and was removed in v2. Rationale: `design.md → v2 redesign`.

The stash and checkout bullets above exist because executors on a shared tree ran `git stash` and `git checkout` and dropped the orchestrator's uncommitted writes. Nothing was lost only because the orchestrator re-applied its writes through the CLI.
